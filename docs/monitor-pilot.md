# Пилот проверки среды интервью (только staging)

Этот пилот по согласию кандидата показывает совпадения с каталогом известных помощников для ответов. Он предназначен для внутреннего теста на отдельном staging-окружении. Совпадение, открытая фоновая вкладка или потеря связи требуют человеческой проверки: они не доказывают использование подсказки, не меняют техническую оценку и не отклоняют кандидата автоматически.

## Подготовка staging

1. Поднимите отдельные приложение, PostgreSQL и приватный бакет для тестовых данных. Примените миграцию `0003_monitor` через обычный запуск `scripts/migrate.py`. Не направляйте тестовые компоненты и миграцию на production БД.
2. Только в staging задайте `MIMAS_ENV=staging` и `MIMAS_MONITOR_ENABLED=1` вместе с обычной конфигурацией MIMAS и приватным `MIMAS_ADMIN_KEY`. Функция включается, лишь когда выполнены **оба** условия. При `MIMAS_ENV=production` она остаётся выключенной даже при `MIMAS_MONITOR_ENABLED=1`; маршруты подключения, каталога и администрирования возвращают 404, а статус интервью сообщает `enabled: false`. Текущий `render.yaml` задаёт production и не включает пилот.
3. Используйте HTTPS-адрес staging для приложения и обоих компонентов. Расширение в репозитории настроено на `https://mimas-staging.onrender.com` в `monitor/extension/manifest.json` (`host_permissions`) и `monitor/extension/background.js` (`BASE`). Если адрес staging другой, замените его **в обоих файлах** перед загрузкой расширения. Windows-помощник использует тот же адрес по умолчанию; для другого staging задайте `MIMAS_MONITOR_URL` при запуске. Помощник допускает HTTP только для `localhost`/`127.0.0.1`.

Проводите пилот на тестовой вакансии с согласившимися участниками. Доступ к отчёту получает компания-владелец вакансии, а не любой работодатель.

## Установка и подключение на Windows

Нужны Windows, .NET 8 SDK для сборки и Chrome/Edge версии 120 или новее. Помощник не требует прав администратора. Для тестового пакета из корня репозитория выполните:

```powershell
dotnet publish .\monitor\windows\Mimas.Monitor.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -o .\monitor\dist\windows
```

Передайте участнику собранный Windows-помощник и папку `monitor/extension` из проверенного staging-коммита. В Chrome откройте `chrome://extensions`, в Edge — `edge://extensions`; включите режим разработчика и выберите «Загрузить распакованное расширение», указав эту папку. Расширение не собирается npm-командой. При изменении его staging-адреса перезагрузите расширение на странице управления.

Кандидат открывает интервью по своей ссылке и подтверждает отдельное согласие на проверку. Интерфейс определяет Windows и показывает две кнопки для **разных** одноразовых кодов:

1. Получите код Windows-помощника. Запустите `Mimas.Monitor.exe` и вставьте код в консоль. Если staging размещён по другому адресу, сначала задайте в PowerShell `$env:MIMAS_MONITOR_URL = 'https://ваш-staging-хост'` в том же окне.
2. Получите новый код расширения, откройте его значок в Chrome/Edge и вставьте код там. Коды действуют пять минут и принимаются только один раз своим компонентом; не публикуйте их вместе с интервью-ссылкой.
3. Дождитесь статуса «Подключён» у обоих компонентов. Только после этого на Windows можно получить первый вопрос. Для платформы `other` требуется согласие, но подключение Windows-компонентов не требуется; названия программ на такой платформе недоступны.

Во время интервью держите консоль помощника и браузер открытыми. Помощник отправляет сигнал присутствия примерно каждые 15 секунд, расширение проверяет вкладки по событиям и таймеру примерно каждые 30 секунд. После начала интервью потеря связи показывается кандидату и компании, но не прерывает интервью. В конце остановите помощник через Ctrl+C и расширение кнопкой «Остановить проверку». Для нового интервью получите новые коды: токен компонента действует до шести часов и привязан к одному интервью.

## Каталог проверенных признаков

Миграция добавляет восемь продуктов с доменами, указанными в публичных источниках. Домен сопоставляется только с HTTPS-хостом или его DNS-поддоменом; похожее окончание имени не подходит. Исходный каталог **не содержит** имён `.exe`, издателей и заголовков окон. Поэтому без ручной проверки установленной программы Windows-помощник не должен показывать совпадения по ней.

Правило для администратора каталога: добавляйте продукт и домен лишь после проверки официального HTTPS-источника и фактического адреса сервиса. Для `executable`, `window_title` и `publisher` сначала установите конкретную версию программы на тестовой Windows, проверьте реальное имя файла/издателя/окна и отрицательные случаи на обычных программах. Запишите HTTPS-источник каждого признака. API требует `verified_installation: true` для недоменных признаков; этот флаг подтверждает ручную проверку оператора, а не выполняет её сам. Не добавляйте общий заголовок окна как единственный признак: помощник требует связанное имя исполняемого файла или издателя. При сомнении оставьте признак выключенным. Не делайте выводов о скрытой программе по одному названию браузерной вкладки.

Каталогом управляет только администратор staging с заголовком `X-Admin-Key`: `GET/POST /api/monitor/admin/products`, `PATCH /api/monitor/admin/products/{product_id}`, `POST /api/monitor/admin/products/{product_id}/signatures`, `PATCH /api/monitor/admin/signatures/{signature_id}`. Сначала проверьте запись через `GET`, затем включайте нужный признак; `enabled: false` у продукта или признака исключает его из выдачи. Компоненты обновляют каталог примерно каждые пять минут. Изменения каталога относятся к последующим сканированиям и не превращают прошлые наблюдения в доказательство нарушения.

## API, доступ и данные

| Кто и чем подтверждает доступ | Маршруты | Назначение |
| --- | --- | --- |
| Кандидат, `X-Interview-Token` | `GET /api/ai/sessions/{iid}/monitor/status`, `POST .../consent`, `POST .../pair` | Статус, согласие до первого вопроса, отдельный код для `helper` или `extension`. |
| Компонент | `POST /api/monitor/claim` | Обмен одноразового кода и типа компонента на токен, привязанный к интервью. |
| Компонент, `X-Monitor-Token` | `GET /api/monitor/catalog`, `POST /api/monitor/heartbeat`, `POST /api/monitor/observations`, `POST /api/monitor/disconnect` | Каталог, присутствие, изменения совпадений и остановка. |
| Компания-владелец, `X-Company-Key` | `GET /api/market/company/assessments/{iid}/monitor` | Наблюдения и сводка только своего интервью. Чужое интервью возвращает 404. |
| Администратор, `X-Admin-Key` | `/api/monitor/admin/...` | Управление продуктами и признаками каталога. |

Помощник локально смотрит имена процессов и видимых окон, положение активного окна и наложений; расширение локально сравнивает адреса вкладок с каталогом. На сервер отправляются только ID совпавшего продукта, тип события (`running_process`, `foreground_window`, `topmost_overlay`, `background_tab` или `active_tab`), состояние `detected`/`cleared` и ID события. Сервер добавляет время, интервью и компонент; отдельно фиксирует потерю/восстановление связи. Полный список процессов, URL посторонних вкладок, скриншоты, содержимое окон и их исходные заголовки не отправляются. Это описание относится к данным мониторинга; обычная запись интервью и ответы регулируются основным согласием MIMAS.

Одноразовые коды и токены компонентов хранятся на сервере как хэши. Расширение держит выданный токен в `chrome.storage.session`, помощник — в памяти процесса. Доступ к деталям наблюдений ограничен токеном кандидата и ключом компании-владельца. Подробные события удаляются после 30 дней при последующих запросах к API; суммарные счётчики обнаружений остаются без заданного срока удаления. Очистка выполняется частями на запросах, поэтому 30 дней — порог удаления, а не обещание удаления в точную минуту. Отчёт указывает `automatic_penalty: false`.

## Проверка пилота

Из корня репозитория запустите проверки логики без подключения внешних сервисов:

```powershell
.venv\Scripts\python.exe -m pytest backend\test_monitor.py -q
node --test monitor\extension\tests\matcher.test.mjs
dotnet run --project .\monitor\windows\Mimas.Monitor.csproj -- --self-test
```

Затем проведите сквозной тест на staging:

1. Создайте тестовую вакансию и интервью. До согласия первый вопрос недоступен. На Windows после согласия подключите оба компонента: статус каждого станет «Подключён», затем первый вопрос откроется.
2. Откройте в Chrome/Edge HTTPS-домен из проверенного каталога сначала в фоне, затем как активную вкладку. Убедитесь, что видны разные типы наблюдения. Похожий домен и HTTP-страница не должны совпасть. Для Windows-событий используйте только отдельно проверенную локальную сигнатуру; исходные восемь продуктов проверяют домены расширением.
3. Остановите компонент во время интервью и дождитесь предупреждения о потере связи; продолжение ответа должно работать. Переподключите его новым кодом и проверьте восстановление связи.
4. Откройте отчёт компании-владельца и проверьте те же наблюдения без автоматического штрафа. Ключом другой компании запросите этот маршрут: ожидается 404.
5. Отключите флаг пилота и убедитесь, что статус сообщает `enabled: false`, а маршруты подключения и каталога возвращают 404. Не включайте флаг в production и не устанавливайте staging-расширение для рабочих интервью.
